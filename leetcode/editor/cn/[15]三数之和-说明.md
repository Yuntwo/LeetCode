# [15] 三数之和 - 题解说明

## 一、标准解法：排序 + 固定最左值 + 双指针

这道题的经典做法是：

1. 先对数组排序。
2. 枚举三元组中的第一个数 `nums[i]``，把它视为当前三元组的最左值。`
3. 在区间 `[i+1, n-1]` 中用双指针 `left` 和 `right` 查找另外两个数，使得：

```go
nums[i] + nums[left] + nums[right] == 0
```

### 为什么排序？

排序后有两个核心收益：

- **方便双指针移动**：
  - 和太小，`left++`
  - 和太大，`right--`
- **方便去重**：相同元素会排在一起，可以直接跳过重复值。

---

## 二、为什么固定“最左值”是最自然的写法？

排序后，任意一个合法三元组都可以写成：

```text
[a, b, c]，且 a <= b <= c
```

标准解法中：

- `i` 只负责枚举 `a`
- `left` 和 `right` 在 `i` 的右侧查找 `b` 和 `c`

也就是说：

> 每个三元组只会在它的最小值 `a` 被枚举到时出现一次。

因此，这种写法的结构最清晰，也最容易证明“不漏解”和“不重解”。

---

## 三、结果集如何去重？

去重一共分两层。

### 1. 外层去重：第一个数去重

如果：

```go
nums[i] == nums[i-1]
```

说明当前这个值之前已经作为三元组第一个数处理过了，再做一次只会产生重复结果，因此直接跳过：

```go
if i > 0 && nums[i] == nums[i-1] {
    continue
}
```

### 2. 内层去重：第二、第三个数去重

当找到一个解后：

```go
nums[i] + nums[left] + nums[right] == 0
```

此时要先记录答案，然后同时移动两端，并跳过连续重复值：

```go
left++
right--
for left < right && nums[left] == nums[left-1] {
    left++
}
for left < right && nums[right] == nums[right+1] {
    right--
}
```

这样可以保证：

- 相同的最左值只处理一次
- 在同一个最左值下，相同的后两个值组合也只记录一次

所以结果集不会重复。

---

## 四、标准写法的执行逻辑

### 初始化

```go
sort.Ints(nums)
```

### 枚举第一个数

```go
for i := 0; i < n-2; i++ {
```

因为至少还需要两个数，所以 `i` 只需要枚举到 `n-3`。

### 剪枝

如果当前 `nums[i] > 0`，因为数组已经有序，后面的数都只会更大，不可能再有三数之和为 `0`，可以直接结束：

```go
if nums[i] > 0 {
    break
}
```

### 双指针移动规则

```go
sum := nums[i] + nums[left] + nums[right]
```

- `sum == 0`：记录答案，然后去重
- `sum < 0`：说明和太小，`left++`
- `sum > 0`：说明和太大，`right--`

---

## 五、标准解法的时间复杂度和空间复杂度

### 时间复杂度

- 排序：`O(n log n)`
- 外层枚举 `i`：`O(n)`
- 每次双指针扫描：`O(n)`

总时间复杂度：

```text
O(n^2)
```

因为 `O(n^2)` 大于 `O(n log n)`，最终整体复杂度为 `O(n^2)`。

### 空间复杂度

如果不算返回结果，额外空间复杂度为：

```text
O(1)
```

如果把排序的实现细节算进去，某些实现会写成 `O(log n)` 栈空间；但面试和题解里通常写额外空间 `O(1)`。

---

## 六、和“以 i 为中心值去找”这种思路的差异

你提到的另一种思路是：

- 固定某个 `i`
- 让 `left` 在左边、`right` 在右边
- 保持 `left < i < right`
- 让 `nums[left] + nums[i] + nums[right] == 0`

这种思路本质上是：

> 把 `nums[i]` 当成三元组的“中间值”来找左右配对。

它**不是错误的**，理论上也能做，而且时间复杂度仍然可以做到 `O(n^2)`。

但它和标准解法相比有几个明显区别。

### 1. 标准解法固定的是“最左值”，中心法固定的是“中间值”

标准解法里：

```text
i -> 最小值
left/right -> 在右边找另外两个值
```

中心法里：

```text
i -> 中间值
left -> 左边找一个
right -> 右边找一个
```

### 2. 中心法跨不同数值的中心通常不会重复，但跨相同中心值会重复

例如：

```text
[-1, 0, 0, 1]
```

若把 `0` 当中心：

- `i = 1` 可以找到 `[-1, 0, 1]`
- `i = 2` 也可以找到 `[-1, 0, 1]`

所以：

> 中心法也不是天然去重的，遇到相同的中心值时，同一个结果仍然可能被找到多次。

因此它同样需要外层去重。

### 3. 中心法实现起来边界更绕

因为需要始终保证：

```text
left < i < right
```

双指针移动时要额外注意：

- 不能让 `left` 越过 `i`
- 不能让 `right` 越过 `i`
- 去重时也要顾及 `i` 在中间的边界

相比之下，标准解法中 `left` 和 `right` 永远都在 `i` 的右边，逻辑更统一。

### 4. 标准解法更容易剪枝

标准解法有一个很自然的剪枝：

```go
if nums[i] > 0 {
    break
}
```

因为最左值都大于 `0` 了，后面不可能再凑出和为 `0`。

而“固定中心值”的写法通常没有这么直接、这么干净的剪枝条件。

### 5. 两者时间复杂度同阶，但标准解法常数更优、代码更稳

两种思路的量级都可以是：

```text
O(n^2)
```

但标准解法：

- 搜索区间更规整
- 去重更自然
- 剪枝更方便
- 边界更少
- 更符合题目的主流解法模板

所以实际编码时，通常都采用“固定最左值 + 双指针”的方案。

---

## 七、两种思路的复杂度对比

### 方案 A：固定最左值（标准解法）

- 时间复杂度：`O(n^2)`
- 空间复杂度：`O(1)`（不算结果）

### 方案 B：固定中心值（可行但不推荐）

- 时间复杂度：`O(n^2)`
- 空间复杂度：`O(1)`（不算结果）

### 为什么最终还是选方案 A？

不是因为中心法的复杂度更差，而是因为：

- 去重证明更麻烦
- 边界更复杂
- 剪枝不如标准法直接
- 实际写起来更容易出错

所以标准题解几乎都采用方案 A。

---

## 八、标准解法代码模板（Go）

```go
func threeSum(nums []int) [][]int {
    sort.Ints(nums)
    n := len(nums)
    res := make([][]int, 0)

    for i := 0; i < n-2; i++ {
        if i > 0 && nums[i] == nums[i-1] {
            continue
        }
        if nums[i] > 0 {
            break
        }

        left, right := i+1, n-1
        for left < right {
            sum := nums[i] + nums[left] + nums[right]
            if sum == 0 {
                res = append(res, []int{nums[i], nums[left], nums[right]})
                left++
                right--
                for left < right && nums[left] == nums[left-1] {
                    left++
                }
                for left < right && nums[right] == nums[right+1] {
                    right--
                }
            } else if sum < 0 {
                left++
            } else {
                right--
            }
        }
    }

    return res
}
```

---

## 九、一句话总结

这题最推荐的做法是：

> **排序 + 固定最左值 + 双指针 + 两层去重**

其原因是：

- 不漏解
- 易去重
- 易剪枝
- 时间复杂度稳定为 `O(n^2)`
- 空间复杂度为 `O(1)`（不算答案）

而“固定中心值”的思路虽然也能做，但实现更绕、去重更麻烦，因此不作为首选。

## 十、为什么 `sum < 0` 时可以直接 `left++`，`sum > 0` 时可以直接 `right--`？

这个地方的核心不是“试一试”，而是：

> **每一步移动都能借助排序性质，排除掉一整片不可能区域。**

固定最左值 `nums[i]` 之后，我们在有序数组中考察：

```go
sum := nums[i] + nums[left] + nums[right]
```

### 1. 当 `sum < 0` 时，为什么可以直接 `left++`？

如果：

```text
nums[i] + nums[left] + nums[right] < 0
```

说明当前和太小，必须让和变大。由于数组已经有序，`right` 左边的数只会更小，所以如果保持当前 `left` 不变，那么：

```text
nums[i] + nums[left] + nums[right'] <= nums[i] + nums[left] + nums[right] < 0
```

其中 `right' <= right`。

也就是说：

> 对当前这个 `left` 而言，搭配任何不超过当前 `right` 的位置，和都不可能达到 `0`。

所以当前这个 `left` 已经没有继续保留的价值，可以直接淘汰，执行：

```go
left++
```

### 2. 当 `sum > 0` 时，为什么可以直接 `right--`？

如果：

```text
nums[i] + nums[left] + nums[right] > 0
```

说明当前和太大，必须让和变小。由于数组已经有序，`left` 右边的数只会更大，所以如果保持当前 `right` 不变，那么：

```text
nums[i] + nums[left'] + nums[right] >= nums[i] + nums[left] + nums[right] > 0
```

其中 `left' >= left`。

也就是说：

> 对当前这个 `right` 而言，搭配任何不小于当前 `left` 的位置，和都不可能达到 `0`。

所以当前这个 `right` 也可以直接淘汰，执行：

```go
right--
```

### 3. 这意味着搜索区域在单调收缩

对于固定的 `i`，候选解空间可以理解为所有满足：

```text
i < left < right < n
```

的二元组 `(left, right)`。

双指针的移动规则只有两种：

- `left++`
- `right--`

因此：

- `left` 只会向右走，不会回退
- `right` 只会向左走，不会回升

所以搜索路径一定是**单调向内收缩**的，不可能回头。

### 4. 为什么不会出现“交叉回来再查”的情况？

比如固定 `nums[i] = -15`，当前看到了：

```text
(-15, 5, 10)
```

后续继续向内收缩，可能会走到：

```text
(-15, 6, 9)
```

这是合理的，因为：

- 左端点变大了
- 右端点变小了

但不会出现：

```text
(-15, 5, 10)
之后又回去看
(-15, 4, 9)
```

因为这要求 `left` 从 `5` 回退到 `4`，而双指针算法中 `left` 永远不会左移。

更重要的是，如果先前某一步已经证明：

```text
(-15, 4, 10) < 0
```

那么以 `4` 作为左端点、右端点不超过 `10` 的所有组合都会小于 `0`，例如：

```text
(-15, 4, 9)
(-15, 4, 8)
...
```

这些组合在逻辑上已经被整体排除了，因此根本不需要回头再检查。

### 5. 这一点保证了：不漏解，也不重复遍历无效区域

所以双指针并不是“凭经验移动”，而是在每次比较后，基于有序性直接排除一整块不可能区域。也正因为如此：

- 不会漏掉合法解
- 不会回头检查已经排除的区域
- 不会出现你提到的那种 `(5,10)` 和 `(4,9)` 这种交叉回查情况

一句话概括：

> **双指针不是在枚举所有二元组，而是在有序数组上沿着一条单调路径收缩搜索空间。**
